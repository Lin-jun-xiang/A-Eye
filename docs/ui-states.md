# 畫面狀態全集 — 每一種偵測情境長什麼樣、為什麼這樣設計

> 這份文件窮舉 `src/main.js` 的 `renderBadges()` / `setStatus()` 與 `src/ui/overlay.js`
> 的所有繪製分支。用途有三個：
>
> 1. **實機測試對照表** —— 看到某個畫面，可以立刻回推「pipeline 現在處於什麼狀態」
> 2. **改 UI 前的清單** —— 動 `renderBadges()` 之前先確認 16 種情境都還成立
> 3. **設計意圖記錄** —— 每個狀態為什麼要顯示、為什麼用這個顏色、為什麼講這句話
>
> 這裡只寫「畫面」。判定邏輯本身請看 [README 的核心原理](../README.md#核心原理為什麼改測尺度變化率)。

## 通用讀法

### 徽章會疊加

`renderBadges()` 是往一個陣列裡「堆」徽章，不是選一個。所以多數實機畫面同時有 2~3 條，
順序固定為：**剛觸發的事件 → 自車狀態 → 前車追蹤 → 紅綠燈 → 錄影中**。

唯一的例外是「兩項偵測都關掉」，那條會提早 `return`（[main.js:159](../src/main.js#L159)），
不再往下堆任何東西 —— 因為此時任何追蹤或紅綠燈資訊都是誤導。

### 四種徽章顏色的語意

| 樣式 | 顏色 | 什麼時候用 | 意圖 |
|---|---|---|---|
| `.move` | 藍 | 前車已起步（觸發） | 事件已發生、需要你動作 |
| `.green` | 綠 | 綠燈了（觸發） | 同上，但來源是燈號 |
| `.red` | 紅 | 紅燈 / 錄影中 / 啟動失敗 | 「注意，但不是要你現在動」 |
| `.idle` | 半透明白 | 其餘全部 | 背景資訊，刻意壓低對比不搶注意力 |

注意 **紅燈用 `.red`、綠燈用 `.green`，但「綠燈了！」的觸發也用 `.green`** ——
兩者靠字級區分（觸發用 `.big`，15px 粗體）。行車中一眼掃過時，字級比顏色更快讀出優先級。

### 兩條證據進度條（z 與 LLR）

畫在目標框正下方（[overlay.js:_drawEvidence()](../src/ui/overlay.js)），分子是當下值、分母是門檻，
所以看到的是「離觸發還差多少」的比例，撞到 100% 就從原色變綠：

| 條 | 顏色 | 公式 | 回答的問題 |
|---|---|---|---|
| `z` | 藍 `#38bdf8` | `z_kf / z_fire`，`z_kf = V/σ_V`，門檻 3.72σ（由 α=1e-4 反推） | **此刻**遠離速度在統計上顯著不等於零嗎 |
| `LLR` | 紫 `#a78bfa` | `llr / A`，`A = ln((1−β)/α) = 9.16` | 從剛剛**累積**到現在，證據夠不夠推翻「車是靜止的」 |

兩條必須同時滿格才觸發（`config.departure.requireBoth`），因為它們互補：

- **z 單獨用會漏掉慢速起步** —— `V` 小、撐不到 3.72σ，但持續累積能過 LLR
- **LLR 單獨用會漏掉快速起步** —— 瞬間很強，但 tick 數不夠累積
- **z 單獨用會誤放單一離群 tick**；**LLR 單獨用會誤放長時間的微小系統性偏壓**（例如對焦呼吸）

LLR 有 z 沒有的三個性質：會累積、會隨時間衰減（`τ = 1.2s`）、掉到下門檻 B 就歸零。
而單 tick 的 `z_raw` 被夾在 ±3，單筆最多貢獻 `2×3 − 2 = 4.0` < 9.16 ——
**結構上不可能單幀觸發**，這正是 v6 最大的洞（40 個特徵點被當成 40 筆獨立觀測，證據膨脹約 30 倍）。

### 狀態列的點與文字

- **綠點脈動** = pipeline 正在跑；**灰點靜止** = 停止或啟動失敗
- 文字在啟動前是操作指示、啟動後換成**裝置資訊**（模型／後端／解析度／有無 IMU）。
  這是實機診斷第一眼要看的東西 —— 「為什麼很慢」通常在這一行就有答案（掉到 wasm 後端、相機給了 1920x1080）
- 右側速度：有 GPS 速度顯示 `km/h`，`unknown` 顯示 `-- km/h`，其餘顯示自車狀態文字

### 01 冷啟動 · 尚未按下開始

| | |
|---|---|

| 狀態列 | 灰點 ·「點擊下方按鈕開始偵測」 |
| 徽章 | `.idle` ⏳ 等待啟動... |

**意圖**：🚩⏺🖼 三個按鈕此時全部 `display:none`。錄影、子母畫面、標註在沒有畫面時毫無意義，
顯示出來只會讓使用者去點一個沒反應的東西。

### 02 啟動中 · 三段前置作業

| | |
|---|---|
| 觸發條件 | 依序跑「開啟相機 → 要求動作感測器授權 → 載入偵測模型」 |
| 狀態列 | 綠點 · 三段文字依序替換 |

**意圖**：三段拆開講，因為三段的失敗原因完全不同（權限 / 感測器 / 網路或 WebGPU），
卡住時使用者自己就能判斷是哪一關。合成一句「啟動中」會讓 iOS 上要等好幾秒的模型下載看起來像卡死。

### 03 啟動成功 · 狀態列變成裝置資訊

| | |
|---|---|
| 觸發條件 | 模型就緒，`frames.start()` 已開始 |
| 狀態列 | 綠點 ·「yolov8n @webgpu 384px · 1280x720 · IMU」 |
| 徽章 | `.idle` ⏳ 載入光流引擎中... |
| 控制列 | 紅色「停止」+ ⏺ 🖼 🔍 |
| 程式 | [main.js:239](../src/main.js#L239) |

**意圖**：OpenCV.js 約 10MB，刻意做成**非阻斷式載入** —— 紅綠燈偵測和 YOLO 追蹤在這期間已經可用，
只有起步判定還沒開始。所以這裡不是「載入中請稍候」的全螢幕遮罩，而是一條可以被忽略的徽章。

### 04 啟動失敗 · 錯誤全文上畫面

| | |
|---|---|
| 觸發條件 | 相機權限被拒 / 模型抓不到 / WebGPU 不支援 |
| 狀態列 | 灰點 ·「❌ NotAllowedError: Permission denied」 |
| 徽章 | `.red` 錯誤全文（HTML 已轉義） |
| 程式 | [main.js:262](../src/main.js#L262) |

**意圖**：**刻意顯示錯誤全文，不做友善包裝。** 手機上沒有 console，
「請確認權限」會把真正的原因（模型 404、CORS、WebGPU 不支援）整個蓋掉，
變成無法遠端診斷的黑箱。友善度輸給可診斷性。

## 二、待機（6 種）

### 05 尋找前車

| | |
|---|---|
| 觸發條件 | 自車靜止、光流就緒，但走廊內沒有夠可信的目標 |
| 徽章 | `.idle` 👀 尋找前車... |
| 程式 | [main.js:174](../src/main.js#L174) |

**意圖**：和「載入光流引擎中」明確區分。兩者畫面都沒有框，但前者是**還沒準備好**、
後者是**準備好了但沒看到車** —— 使用者的反應應該不同（等 vs 調整手機角度）。

### 06 自車行駛中 · 靜默

| | |
|---|---|
| 觸發條件 | GPS／IMU／視覺三路融合判定自車在動 |
| 狀態列 | 右側顯示實際速度，例「42 km/h」 |
| 徽章 | `.idle` 🚙 行駛中 — 靜默中 |
| 程式 | [main.js:165](../src/main.js#L165) |

**意圖**：「靜默中」三個字是**刻意寫出來的**。起步警示是給停著等紅燈用的，
行駛中必須閉嘴；但如果畫面完全不提，使用者會以為 App 壞了或忘記開。
要讓「沒有警示」看起來是個**主動決定**，而不是故障。

### 07 自車狀態未知

| | |
|---|---|
| 觸發條件 | GPS 沒定位、IMU 也沒授權 |
| 狀態列 | 右側「-- km/h」，裝置資訊顯示「無IMU」 |
| 徽章 | `.idle` ❓ 自車狀態未知（等待 GPS / IMU） |
| 程式 | [main.js:167](../src/main.js#L167) |

**v7.1 補的洞**：這一條原本還有一個更隱蔽的版本 —— GPS 停在路口時會漂移到
2~5 km/h，把狀態鎖進 MOVING，於是畫面顯示的是 06「行駛中 — 靜默中」而不是這一條。
使用者看到「行駛中」卻明明停著，根本不會想到是 GPS 的問題。
現在進入 MOVING 需要持續 1.2 秒超過門檻，且低速時可被背景尺度證據否決
（面板會顯示 `[視覺否決GPS漂移]`）。

**意圖**：`unknown` 是 v7 新增的**第三狀態**。v6 只有布林值且「不可用時維持上一狀態」，
初值 `false` 導致 GPS 一失效就行駛中也照報；反之會永久靜默。
明確分出 unknown 之後，預設不通知（可用 `config.ego.unknownIsStill` 改變），
而且這條徽章讓使用者知道**為什麼**不通知。

### 07b 影片模式（📁）

| | |
|---|---|
| 觸發條件 | 按 📁 選了一個影片檔（取代相機） |
| 狀態列 | `模型 @webgpu 640px · 影片 720x1280`（沒有 IMU 欄位） |
| 徽章 | `.idle` 📁 影片模式（＋自車狀態徽章，來自影片自己的視覺判定） |
| 程式 | `frameSource.js` `startFile()` · `pipeline.assumeStill` |

**意圖**：影片檔沒有 GPS / IMU，但**影片自己就能判斷自車動不動** ——
判定降級到「背景尺度變化率」那一路，面板顯示 `行駛中（visual-scale z=18.3）`。

第一版做錯了：原本直接強制假設自車靜止。丟一支 189 秒的行駛影片進去，
行駛中前車自然一直在遠離 → 40 秒內報了 5 次「前車已起步」。
那不是判定失準，是**用假設取代了量測**。現在要勾選
「🛑 強制假設自車靜止」才會回到那個行為（適合光流還沒運作的片段），
而且勾選狀態會寫在徽章上 —— 假設必須可見。

錄影按鈕在影片模式下會隱藏（沒有 MediaStream 可錄）。
影片會用 `object-fit: contain` 顯示（相機模式是 `cover`）：手機直式影片放到
桌機橫向視窗時，`cover` 的縮放倍率是 `max(寬比, 高比)`，會把畫面放大到只剩
中間一條。`overlay.fit` 必須跟著切換，否則框會畫在錯的位置。

**底部只留兩條徽章**（事件 + 模式），其餘資訊全部搬到分析面板 ——
同一份資訊出現兩次不會更清楚，只會互相重疊。

### 07c 影片分析面板（影片模式專用）

| | |
|---|---|
| 觸發條件 | 影片模式啟動時自動出現（右上角） |
| 內容 | 影片時間、自車、前車、剎車燈、**第三剎車燈**（狀態/值/峰值/位置）、燈位準/峰值/門檻、起步證據條、未觸發原因、光流 ok 比例、偵測次數 + **事件時間軸** |
| 程式 | [analysisPanel.js](../src/ui/analysisPanel.js) |

**意圖**：徽章是為「開車中掃一眼」設計的 —— 資訊量壓到最低、疊在畫面上、
內容隨狀態變動。拿它來分析影片剛好每一項都是缺點。分析的需求是相反的：
**資訊要多、位置要固定、數值不能閃**。所以：

1. 行的結構固定（標籤 + 值），只改 `textContent`，不重建 DOM
2. 固定 5Hz 更新，且**值沒變就不寫 DOM**
3. 進度條用固定 8 格的字元（`████····`），寬度不隨數值改變 → 不會重排
4. 事件用**時間軸累積**，不是停留 3 秒的徽章 ——
   影片分析最重要的問題是「有沒有在正確的時間點觸發」，
   而一閃即逝的徽章正好答不了這個問題

### 為什麼徽章原本會閃到讀不出來

三個原因疊在一起，缺一個都不會這麼嚴重：

| 原因 | 修法 |
|---|---|
| `renderBadges()` 每一幀（30Hz）都被呼叫 | 限流到 5Hz |
| 每次都重建 `innerHTML` → 瀏覽器丟掉整棵子樹重排 | **內容沒變就不寫 DOM**（`alerts.js`）—— 只限流不夠，5Hz 重建一樣會閃 |
| 內容本身在跳：證據百分比逐幀變動、剎車燈狀態在對比邊界上跳成 `不確定` | 百分比量化到 5% 一格；剎車燈狀態要求新狀態持續 400ms 才換（只影響顯示，判定有自己的 `offConfirmMs`） |

### 08 兩項偵測都關掉

| | |
|---|---|
| 觸發條件 | 兩個 checkbox 都取消 |
| 徽章 | `.idle` ⚠️ 所有偵測項目皆已關閉（唯一一條） |
| 程式 | [main.js:159](../src/main.js#L159) |

## 三、追蹤（3 種）

### 09 鎖定前車 · 證據累積中

| | |
|---|---|
| 觸發條件 | 最常見的畫面。目標鎖定、光流量測正常 |
| Overlay | **實線綠框** + 框下 `z`／`LLR` 兩條進度條 + TTC |
| 徽章 | `.idle` 🚗 追蹤前車 #3｜證據 42%｜TTC 18s｜llr-low｜剎車燈 亮 |
| 程式 | [overlay.js:_drawEvidence()](../src/ui/overlay.js) · [main.js:181](../src/main.js#L181) |

最後一欄是 `departure.lastReason`（`llr-low` / `z-low` / `below-min-ttc` / `no-upward`
/ `dwell` / `few-ticks` / `cooldown` / `untrusted` / `ego-moving`）——
**實車測試時手機沒有 console**，只看得到百分比的話無法區分
「訊號真的不足」和「某一道閘門卡住」，那正是 v7 首次路測最難查的問題。

**意圖**：徽章的「證據 %」是 `z/z_fire` 夾到 0~100，只給一個數；
真正的兩維資訊在框下的進度條上。**兩層資訊密度是刻意的** ——
掃一眼看徽章，要細查看框下。track id 要顯示，因為切換目標是最需要診斷的行為。

### 10 背景不可信

| | |
|---|---|
| 觸發條件 | IMU 陀螺儀預測與視覺背景殘差差超過 4σ |
| Overlay | ROI 框從藍轉**紅**虛線 |
| 徽章 | `.idle` 🚗 追蹤前車 #3｜證據 38%｜untrusted｜剎車燈 亮｜⚠背景不可信 |
| 程式 | [main.js:186](../src/main.js#L186) · `departure.js` `coast()` |

**意圖**：通常是旁邊車道整排車在動，RANSAC 鎖到移動車群 —— v6 在這個情境會直接誤報起步。
v7 把該 tick 標記不可信、證據不累積。畫面上必須看得出來，
否則使用者會以為「證據卡在 38% 不動」是 bug。

### 11 目標暫時遺失 · coast 中

| | |
|---|---|
| 觸發條件 | 超過 1.8 個偵測週期沒有新的偵測更新該 track，Kalman 繼續外推 |
| Overlay | **虛線**綠框；進度條數值凍結不動 |
| 程式 | `tracker.js` coasting · `overlay.js` `dash:[6,4]` |

**意圖**：實線 vs 虛線是「這是觀測到的」vs「這是預測的」。
v6 在追蹤斷掉時 `ofReleaseAll()` 直接清空 LLR，而**前車起步時 bbox 縮小恰好最容易讓追蹤斷掉**
—— 證據在最該警示的那一刻被清空，這是 v6 漏報的直接機制。
v7 改成 coast 而非歸零，畫面上的虛線就是這個決定的可見證據。

門檻是「1.8 × 偵測週期」而不是固定毫秒數：原本寫死 60ms，但 `detectHz = 8`
代表偵測本來就每 125ms 才來一次，於是**每個框幾乎永遠是虛線**，
虛線就失去了「這是預測的」這個語意。

### 11b 自車結構（引擎蓋 / 儀表板）—— 只在除錯模式可見

| | |
|---|---|
| 觸發條件 | 自車行駛中，某個 track 連續 2 秒完全不動 → 列入黑名單 |
| Overlay | **灰色短虛線框 + 「自車結構」標籤**（僅 debug 模式） |
| 程式 | `frontCar.js` `learnEgoStructure()` · `overlay.js` `_drawEgoRegions()` |

**意圖**：手機放在擋風玻璃內，YOLO 會把引擎蓋、儀表板、玻璃反光認成 `car`。
這種框的底邊在畫面最下方，而前車選取的分數是 `proximity × 走廊權重`，
`proximity` 又直接由底邊高度決定 → **這種假框的分數必定最高，永遠被選成前車**，
於是光流量的是一個永遠不動的東西 —— 起步警示在結構上不可能觸發。

另外有三項**軟性**加權會壓低這種假框的分數（長寬比、`w_px/Δy` 高側離群、
有沒有出現過一對對稱剎車燈），但刻意都不是硬性排除 ——
「底邊太低就排除」會誤殺 3 公尺內底邊被畫面裁掉的真前車，
手機架高看不到引擎蓋時更是純傷害。

黑名單這一層的排除依據是物理性質而不是畫面比例：自車結構相對相機完全靜止，
所以「自車行駛中框卻完全不動」只可能是自車的一部分（路邊停的車在自車前進時 bbox 會放大）。
**只在自車行駛時學習** —— 紅燈停車時前車本來就不動，在那時學習會把真前車列進黑名單。

## 四、警示（4 種）

### 11d 前車踩下剎車（無聲事件）

| | |
|---|---|
| 觸發條件 | 車頂中央的第三剎車燈由暗轉亮、持續 200ms，且自車靜止、目標已武裝 |
| 徽章 | `.red` ⏸ 前車踩下剎車（可能正在打檔）（停留 2.5 秒） |
| 輸出 | **無聲、不震動、不閃** |
| 程式 | `brakeLight.js` `_updateChmsl()` · `alerts.js` 的 `event.silent` |

**意圖**：自排車從 P/N 打入 D **必須踩剎車**，所以「暗了很久之後亮起」是起步的
前兆 —— 實車量測領先車輛實際移動約 **9 秒**（38.3s 踩下 → 47.4s 車動）。

但 9 秒太早：那麼早出聲只會變成干擾，駕駛會學會忽略它。所以它是**無聲事件** ——
畫面上留下痕跡（尤其是離線分析的時間軸）但不打擾人。`chmsl.alertOnPress` 可開。

這個「暗 → 亮」的轉換**只有第三剎車燈看得到**：外側燈兼作尾燈、全程亮著，
根本不存在這個邊緣。

### 11c 前車鬆開剎車 ⚡ 觸發（快路徑）

| | |
|---|---|
| 觸發條件 | 剎車燈由亮轉熄、持續確認，且自車靜止、目標已武裝。**優先用第三剎車燈**（落差 70 倍、確認 200ms）；看不到它時才退回左右尾燈（落差 1.5 倍、需兩側同時、確認 350ms） |
| Overlay | debug 模式下左右燈區框由**紅轉灰** |
| 徽章 | `.red` 🟠 前車鬆開剎車，準備起步（只停留 **1.5 秒**） |
| 輸出 | 單音 760Hz 0.1s（音量 0.18，正式警示的一半）· 單次震動 90ms · **不閃全螢幕** |
| 程式 | `brakeLight.js` · [pipeline.js](../src/core/pipeline.js) 的 3.5 段 |

**意圖**：這是**預告**不是事實 —— 駕駛可能鬆了剎車卻打 P/N 而不走。
所以三個通道全部刻意做輕：單音、半音量、無閃爍、徽章只留 1.5 秒。
若做得跟「已起步」一樣響，駕駛會分不出「該動了」和「快要該動了」，
而**分不出來的提示等於沒有提示**。

代價是打 P/N 時會誤報一次；這是刻意接受的取捨（塞車與紅燈情境下打 P/N 機率極小），
可用 `config.brakeLight.alertOnRelease = false` 關掉。

### 12 前車已起步 ⚡ 觸發

| | |
|---|---|
| 觸發條件 | 六個條件同時成立（見下） |
| Overlay | 綠框縮小上移；`z`／`LLR` 兩條**都撞 100% 變綠**；TTC 掉到個位數 |
| 徽章 | `.move .big` 🚗 前車已起步！（停留 3 秒）+ 下方保留追蹤徽章 |
| 輸出 | 三段升頻音 880→1180→1480Hz · 震動 120-60-120-60-200 · 藍色全螢幕閃爍 500ms |
| 程式 | [pipeline.js:150](../src/core/pipeline.js#L150) · [alerts.js](../src/ui/alerts.js) |

七個條件：`z_kf ≥ z_fire`、`LLR ≥ A`、`V ≥ minInvTtc`（物理下限）、
`dwell ≥ 260ms` 且 `≥ 4 ticks`、影像往地平線方向移動、自車靜止且背景可信、
目標已被連續追蹤 ≥ `armMs`（鑽車縫掠過的機車與切入車不該武裝）。

**若剎車燈先熄過**（`primed`），`dwell` 放寬到 120ms、ticks 放寬到 2，
且 SPRT 先加上 `ln(0.90/0.02) = 3.81` 的先驗 —— 一個獨立來源的佐證
正當地降低了所需的自我佐證量。這不是偷跑，是貝氏更新。

**意圖**：三通道同時輸出（聲音 / 震動 / 視覺），因為使用情境下任何單一通道都可能失效
—— 手機靜音、放在支架上感覺不到震動、視線在別處。
升頻三音（而非單音）是因為它在車內引擎與冷氣噪音中辨識度最高，且**不像任何車機的既有提示音**。
觸發後 `llr` 歸零但**保留 KF** —— 車還在遠離，不該假裝沒看到。

### 13 紅燈中 · 等待

| | |
|---|---|
| 觸發條件 | 紅綠燈偵測開啟且判定為紅 |
| Overlay | 燈號框轉紅 |
| 徽章 | `.red` 🔴 紅燈（疊在追蹤徽章下） |
| 程式 | [main.js:191](../src/main.js#L191) |

**意圖**：只顯示、不發聲。黃燈共用同一個 `.red` 樣式 ——
兩者對駕駛的意義相同（不要動），不值得多一種顏色。

### 14 綠燈了 ⚡ 觸發

| | |
|---|---|
| 觸發條件 | 燈號框內顏色由紅／黃轉綠並持續 400ms |
| 徽章 | `.green .big` 🟢 綠燈了！起步！ |
| 輸出 | 雙音 660→990Hz · 震動 200-80-200 · 綠色全螢幕閃爍 500ms |
| 程式 | [pipeline.js:170](../src/core/pipeline.js#L170) |

**意圖**：與前車起步是**兩條獨立的觸發路徑**，可以先後各響一次（綠燈亮 → 前車才動）。
音效刻意做成雙音而非三音，讓使用者不用看畫面就能分辨是哪一種事件。

### 16 除錯面板開啟

| | |
|---|---|
| 觸發條件 | 按 🔍 或 `?debug=1` |
| Overlay 額外顯示 | 所有 track 的框與分數、走廊多邊形、地平線、光流 ROI 與其縮放比 |
| 面板 | 各階段耗時 + 實際 Hz + pipeline 內部狀態，每 200ms 重繪一次 |
| 程式 | [hud.js](../src/ui/hud.js) `DebugPanel.render()` · `overlay.js` debug 分支 |

**意圖**：面板刻意 `pointer-events: none`，覆蓋在畫面上但不吃觸控 —— 開著它仍然可以操作 App。
內容的排列順序是「節拍 → 耗時 → 內部狀態」，因為**幀率不對的時候其他數字都不用看**
（LK 光流的 small-motion 假設在低幀率下根本不成立）。
`z 3.14/3.72`、`LLR 3.42/9.16` 這種「當下值/門檻」的寫法讓「還差多少」不需要心算。

**這個面板在 2026-09-08 的夜間路測直接抓出兩個根因**：`flow ok 0/225 | fg-fit-fail:41`
（尺度變化率那條路從沒運作過，因為官方 opencv.js 沒有編入
`estimateAffinePartial2D`）以及 `brake ... on` 但永遠不轉 `off`（夜間亮度飽和，
必須改用面積）。沒有這幾行，這兩件事在畫面上完全看不出差別 ——
這就是它存在的理由。
面板讀法逐行說明見 [README](../README.md#除錯面板讀法)。
